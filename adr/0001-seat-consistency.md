# ADR-0001. Согласованность мест обеспечивает PostgreSQL

## Контекст и постановка задачи

Во время старта продаж несколько реплик API получают запросы на одно место. Удержание действует 15 минут, а конкуренция продолжается и при сбоях Redis, просрочке удержания или позднем ответе платёжного шлюза. Требуется механизм, который сохраняет единственность удержания и продажи для пары «мероприятие, место».

## Драйверы решения

- SYS-F03 требует не более одного действующего удержания или одного билета на место.
- SYS-F02 и SYS-F05 устанавливают 900 секунд и проверку серверного дедлайна.
- SYS-N01 задаёт цель p95 ≤ 300 мс при 500 запросах/с.
- Учебный контур разворачивается через Docker Compose и должен позволять воспроизводить гонки.

## Рассмотренные варианты

- Redis как основной арбитр.
- Только PostgreSQL.
- PostgreSQL как арбитр и Redis как краткий защитный ключ.

## Итог решения

Выбран вариант «PostgreSQL как арбитр и Redis как краткий защитный ключ». Каждому месту события соответствует одна строка EventSeat. Транзакции удержания, продажи и истечения синхронизируются по этой строке через `SELECT ... FOR UPDATE`. Перед записью проверяются текущее удержание, его срок и существование билета. Уникальность Ticket.eventSeatId защищает от повторной продажи и при ошибке вызывающего кода. Redis помогает сгладить всплеск запросов к одному месту. При занятом ключе запрос после короткой задержки проверяет БД, а при недоступном Redis идёт в БД напрямую.

### Последствия

- Бизнес-срок удержания определяется данными и временем PostgreSQL. Истечение технического Redis-ключа не продлевает удержание и не создаёт нового владельца.
- Блокировка строки сохраняется только на время локальной транзакции. Вызовы Camunda и платежей выполняются вне неё.
- Для горячих мест возможны очереди SQL. Требуется измерять ожидание блокировок и ограничивать время ожидания. При недоступной БД API возвращает 503.
- Защитный Redis-ключ остаётся в проекте по результатам сравнительного нагрузочного замера.

### Подтверждение

На двух репликах API запустить 100 одновременных запросов разных сессий на одно свободное место. Проверить одного владельца, ответы 409 для остальных и единственность билета. Повторить после остановки Redis, с истечением ключа и при гонке оплаты с истечением. При 500 RPS сравнить PostgreSQL, выбранный гибрид и экспериментальный вариант Redlock с теми же SQL-инвариантами.

## Плюсы и минусы вариантов

| Вариант | Плюсы | Минусы |
|---|---|---|
| Redis как основной арбитр | Быстрое получение ключа, раннее обнаружение горячего места | Корректность зависит от свойств аренды и конфигурации Redis. Истечение аренды до коммита усложняет согласование с PostgreSQL |
| Только PostgreSQL | Единая транзакционная граница, меньше распределённых зависимостей | Все конкурентные попытки сразу попадают в пул БД, горячие строки могут увеличить задержки |
| PostgreSQL как арбитр и Redis как краткий защитный ключ | Корректность обеспечивается SQL и сохраняется при сбое Redis. Можно сглаживать конкурентные всплески | Дополнительный сетевой вызов и настройка задержек. Польза требует измерений |
