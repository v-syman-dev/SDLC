## 1. Введение {#1-introduction}

### 1.1 Назначение документа {#11-document-purpose}
Настоящий документ определяет спецификацию требований к программному обеспечению (SRS) для «Системы высоконагруженного бронирования билетов». Документ описывает **ЧТО** именно должна делать система, не предписывая конкретных деталей реализации («КАК»). Документ предназначен для разработчиков, тестировщиков, бизнес-аналитиков и преподавателя в рамках выполнения лабораторных работ по дисциплине «Жизненный цикл разработки программного обеспечения».

### 1.2 Область применения продукта {#12-product-scope}
Продукт представляет собой веб-приложение для массовой продажи билетов на культурно-массовые мероприятия (концерты, шоу) с высокой интенсивностью пользовательского трафика. Основное назначение системы — обеспечение интерактивного выбора мест, гарантированная защита от одновременного бронирования (overbooking), временное удержание слотов (TTL 15 минут) и оркестрация процесса оплаты через движок бизнес-процессов. В рамки текущего SRS входит вся логика бэкенда на Kotlin, веб-интерфейс, интеграция с Camunda BPM и симуляция платежного шлюза.

### 1.3 Определения, акронимы и сокращения {#13-definitions-acronyms-and-abbreviations}

| Term | Definition |
|------|------------|
| API | Application Programming Interface — набор протоколов для интеграции ПО |
| SRS | Software Requirements Specification — спецификация требований к ПО |
| Overbooking | Ситуация перепродажи мест, при которой продано больше билетов, чем физически есть в зале |
| TTL | Time-To-Live — время жизни временной брони (15 минут) |
| Camunda | Workflow Engine для оркестрации бизнес-процессов и транзакций (саг) |
| Redis | Высокопроизводительное хранилище данных в памяти, используемое для распределенных блокировок |

## 2. Обзор продукта {#2-product-overview}

### 2.1 Перспектива продукта {#21-product-perspective}
Система является новым самостоятельным веб-приложением. Архитектурно она состоит из клиентской веб-части и серверного ядра на Kotlin (Spring Boot / WebFlux), взаимодействующего с реляционной базой данных (PostgreSQL) для хранения персистентных данных и быстрым кэшем (Redis) для блокировок. Внешняя система проведения платежей представлена изолированным Mock-сервисом.

### 2.2 Функции продукта {#22-product-functions}
* Управление конфигурациями залов (структура секторов, рядов и мест) и динамическое создание мероприятий.
* Интерактивный выбор свободных мест на графической схеме зала.
* Временная блокировка (удержание) выбранных слотов за пользователем на 15 минут.
* Гарантированная защита от overbooking на уровне распределенных блокировок и транзакций БД.
* Оркестрация бизнес-процесса бронирования и оплаты с использованием паттерна «Сага» через Camunda BPM.
* Имитация платежного шлюза с поддержкой сценариев успешной оплаты, сбоя и таймаута.

### 2.3 Ограничения продукта {#23-product-constraints}
* Система должна разрабатываться на языке Kotlin с использованием веб-стека.
* Время удержания неоплаченного места в слоте строго ограничено 15 минутами (TTL).
* Интеграция с реальными банковскими системами заменена программным имитатором (Mock-шлюзом).

### 2.4 Характеристики пользователей {#24-user-characteristics}
* **Покупатель (Фанат):** Конечный пользователь системы. Обладает базовыми навыками работы с web-приложениями, осуществляет выбор мест, временную бронирование и оплату.
* **Администратор / Организатор:** Обладает расширенными правами, управляет справочником залов, создает новые мероприятия и контролирует квоты.

### 2.5 Допущения и зависимости {#25-assumptions-and-dependencies}
* Предполагается наличие стабильного интернет-соединения у клиентов во время интерактивного бронирования.
* Корректность работы TTL-таймеров зависит от синхронизации системного времени бэкенд-серверов.

### 2.6 Распределение требований {#26-apportioning-of-requirements}
Все перечисленные требования реализуются в рамках единого учебного цикла разработки для обеспечения сдачи лабораторных работ.

## 3. Требования {#3-requirements}

### 3.1 Внешние интерфейсы {#31-external-interfaces}

#### 3.1.1 Пользовательские интерфейсы {#311-user-interfaces}
* Веб-интерфейс предоставляет интерактивную схему зала с цветовой индикацией статусов мест (свободно, забронировано, куплено).
* Страница чекаута содержит динамический таймер обратного отсчета (15 минут).
* Графические макеты интерфейсов:
  * [Схема зала и выбор мест](./images/hall-scheme.png)
  * [Экран чекаута и оплаты](./images/checkout-screen.png)

#### 3.1.2 Аппаратные интерфейсы {#312-hardware-interfaces}
* Специальные аппаратные интерфейсы не требуются; используются стандартные сетевые интерфейсы передачи данных.

#### 3.1.3 Программные интерфейсы {#313-software-interfaces}
* RESTful API для обмена данными между фронтендом и бэкендом.
* Внутреннее клиентское API для взаимодействия с Camunda BPM Engine.
* Внешний интерфейс взаимодействия с Mock-платежным шлюзом.

### 3.2 Функциональные требования {#32-functional}

* **REQ-FUNC-001 (Выбор и блокировка места):** Система должна позволять пользователю выбрать свободное место в зале и инициировать его временное удержание сроком на 15 минут.
* **REQ-FUNC-002 (Защита от Overbooking):** Система должна гарантировать исключение одновременного бронирования одного места двумя пользователями с использованием распределенных блокировок (Redis / Pessimistic Locking).
* **REQ-FUNC-003 (Оркестрация процессов через Camunda):** При подтверждении бронирования система должна запускать процесс в Camunda BPM, оркеструющий списание слота, вызов платежного шлюза и фиксацию продажи.
* **REQ-FUNC-004 (Автоматический возврат слота):** При истечении 15 минут и отсутствии подтверждения оплаты система должна автоматически освобождать заблокированное место.
* **REQ-FUNC-005 (Управление каталогом мероприятий):** Администратор должен иметь возможность создавать конфигурации залов и открывать новые события.

### 3.3 Качество обслуживания {#33-quality-of-service}

#### 3.3.1 Производительность {#331-performance}
* Время отклика сервера при обработке запроса на блокировку места не должно превышать 300 мс в условиях пиковой нагрузки до 500 RPS.

#### 3.3.2 Безопасность {#332-security}
* Изоляция пользовательских сессий при бронировании и обязательная валидация входящих данных на уровне бэкенда.

#### 3.3.3 Надёжность {#333-reliability}
* Обеспечение идемпотентности транзакций бронирования и оплаты. При сбое платежа Camunda запускает компенсационную транзакцию.

#### 3.3.4 Доступность {#334-availability}
* Целевой показатель бесперебойной доступности сервиса в периоды старта продаж составляет не менее 99%.

#### 3.3.5 Наблюдаемость {#335-observability}
* Логирование ключевых шагов бизнес-процессов в Camunda Cockpit, фиксация сбоев транзакций и метрик времени удержания слотов.

### 3.4 Соответствие стандартам {#34-compliance}
* Разработка бэкенда ведется в соответствии со стандартами написания кода на языке Kotlin и принципами чистого архитектурного проектирования.

### 3.5 Проектирование и реализация {#35-design-and-implementation}

#### 3.5.1 Установка {#351-installation}
* Контейнеризация и развертывание всех компонентов системы с помощью Docker Compose (PostgreSQL, Redis, Camunda, Kotlin Service).

#### 3.5.2 Сборка и поставка {#352-build-and-delivery}
* Использование системы сборки Gradle и автоматизированная сборка исполняемых артефактов.

#### 3.5.3 Распределение {#353-distribution}
* Развертывание в виде микросервисных или модульных монолитных контейнеров в едином контуре.

#### 3.5.4 Сопровождаемость {#354-maintainability}
* Модульная структура кода, разделение на слои (Web, Business Logic, Persistence, Workflow).

#### 3.5.5 Повторное использование {#355-reusability}
* Выделение универсальных компонентов валидации и работы с блокировками в переиспользуемые модули.

#### 3.5.6 Переносимость {#356-portability}
* Кроссплатформенность за счет использования контейнеров Docker.

#### 3.5.7 Стоимость {#357-cost}
* Минимизация накладных расходов за счет использования открытого технологического стека (Open Source).

#### 3.5.8 Сроки {#358-deadline}
* Реализация проекта строго в рамках графика выполнения лабораторных работ текущего семестра.

#### 3.5.9 Доказательство концепции {#359-proof-of-concept}
* Проведение стресс-тестирования механизма блокировок в условиях высокой конкуренции потоков.

#### 3.5.10 Управление изменениями {#3510-change-management}
* Ведение версионирования кода через Git и использование Pull Request для согласования правок.

### 3.6 ИИ/МО {#36-aiml}
* Компоненты искусственного интеллекта и машинного обучения в рамках текущей версии системы не используются.
